# L7 Process Attribution

Flodbadd provides per-session Layer 7 (L7) process attribution: mapping every
observed TCP/UDP session to the originating process, its path, parent process,
command line, and open files. This is the foundation for EDAMAME's vulnerability
detection and behavioral divergence analysis.

## Architecture

L7 resolution uses two resolution paths:

**Eager path** (inline, per-session): When a new session is observed, the
resolver immediately tries kernel-level sources before queueing. This
catches short-lived connections before the process exits:

```
eBPF connection map (Linux)  →  ES+libproc (macOS)
```

On Windows, `netstat2` (`GetExtendedTcpTable`) is fast enough that no
kernel-level eager path is needed.

**Batch path** (periodic, queued): Sessions that fail the eager path are
queued and resolved in periodic batches using platform socket lookups:

```
netstat2 socket scan  →  port cache  →  host cache  →  retry with backoff
```

The kernel-level sources maintain persistent process and connection tables
that survive short-lived connections; the platform socket lookups are
point-in-time snapshots that can miss processes that have already exited.

## Platform Support

### Linux -- eBPF

| Aspect | Detail |
|---|---|
| Module | `src/l7_ebpf.rs` |
| Feature flag | `ebpf` |
| Documentation | `EBPF.md` |
| Mechanism | kprobes on `tcp_v4_connect` / `tcp_v6_connect` (stash process info keyed by `struct sock *`), `tcp_set_state` (join the 4-tuple on `TCP_ESTABLISHED`) and `__sk_free` (evict). `sched_process_exec` / `_fork` / `_exit` tracepoints feed the process-event ring, not L7. |
| Data maintained | `l7_connections` (4-tuple -> PID, UID, process name and path) and `socket_to_process`, both kernel-side BPF hash maps capped at 65,536 entries |
| Connection mapping | Provided. The 4-tuple to PID join happens in the kernel, which is why Linux resolves instant-close sessions. |
| Privilege | `CAP_BPF` + `CAP_PERFMON` (or root) |
| Architectures | x86_64, aarch64 |
| Limitations | Runtime preflight requires kernel >= 5.3; the process-event ringbuf needs 5.8 and the cgroup hooks 5.7, and those degrade independently. Needs clang/llvm at build time and linux-headers for BTF. |

The eBPF object carries more than L7. Task-access and egress-intent hooks
feed the cross-platform process-event stream and are documented in
`EBPF.md`; they do not participate in session attribution.

### macOS -- Endpoint Security (ES)

| Aspect | Detail |
|---|---|
| Module | `src/l7_es.rs` |
| Feature flag | `endpointsecurity` |
| Documentation | `ENDPOINTSECURITY.md` |
| Mechanism | ES client subscribing to `NOTIFY_FORK`, `NOTIFY_EXEC` and `NOTIFY_EXIT`. The same client also subscribes to file and task-port events for file integrity monitoring and the process-event stream; those play no part in L7 resolution. See `ENDPOINTSECURITY.md`. |
| Data maintained | `DashMap<u32, EsProcessInfo>` (PID -> process name, path, parent PID, parent name, parent path) |
| Connection mapping | Not provided -- ES tracks processes only; socket-to-PID uses `libproc` (`src/l7_macos.rs`) |
| Privilege | Requires `com.apple.developer.endpoint-security.client` entitlement + root |
| Entitlement | Must be provisioned by Apple; ad-hoc signing works with SIP disabled |
| Fallback | Without ES, `l7_macos.rs` provides socket-to-PID via `libproc` plus `sysinfo` for metadata |

The hybrid ES + `libproc` approach (eager path):
1. `get_l7_for_session()` iterates ES-known PIDs and probes their sockets
   via `libproc`, short-circuiting on first match. Only kernel-reported
   PIDs are visited, so this is much faster than a full system socket scan.
2. If ES is unavailable, the batch path uses a full `libproc` scan + `sysinfo`.

### Windows -- netstat2 (GetExtendedTcpTable)

On Windows, the primary L7 resolution mechanism is `netstat2`, which calls
the Win32 `GetExtendedTcpTable` / `GetExtendedUdpTable` APIs from `iphlpapi.dll`.
These return a complete snapshot of all active connections with their owning PIDs
in a single synchronous kernel syscall. This is fast enough to resolve even
instant-close (0 ms) TCP sessions, matching eBPF's coverage on Linux without
requiring any additional kernel-level infrastructure.

### Windows -- Event Tracing for Windows (ETW)

| Aspect | Detail |
|---|---|
| Module | `src/l7_etw.rs` |
| Feature flag | `etw` (enabled in `edamame_helper` and `edamame_posture`) |
| Documentation | `ETW.md` |
| Mechanism | Kernel ETW trace session ("NT Kernel Logger") with the TCP/IP, process and file-IO-init flags, plus a second private session for `Microsoft-Windows-Kernel-Audit-API-Calls` |
| Data maintained | PID -> image path, parent PID, command line; and a connection key -> PID table |
| Connection mapping | Provided by TCP/IP ETW events (Connect, Accept, Reconnect) |
| Privilege | Administrator or LocalSystem required for the kernel trace session |

ETW is enabled in production, but **not because it wins the L7 race**. It does
not. `GetExtendedTcpTable` is a synchronous kernel syscall that sees a
connection immediately, while ETW events arrive asynchronously with buffering
latency, so `netstat2` resolves first on every measured hold duration.

Note that this is an empirical result, not a structural one. ETW is tried
*before* the netstat exact match on both the eager and batch paths, and a hit
is recorded as `L7ResolutionSource::Etw`. The benchmark simply never observes
one. `ETW.md` records an unverified alternative explanation for that: the
TCP/IP decode selects the IPv4 or IPv6 payload by event version alone rather
than by opcode, which could mean IPv4 tuples never key a session at all. Until
that is settled, read "netstat2 wins" as the measured outcome rather than as a
proven latency race.

The lineage enrichment ETW performs applies only to sessions ETW itself
resolved, so in practice it does not reach the netstat-resolved sessions that
make up the measured population.

The two roles that justify the feature are kernel-time file-writer attribution
and the cross-process task-access stream. Both are documented in `ETW.md`.

## Resolution Source Priority

The `FlodbaddL7::try_kernel_resolve()` method in `src/l7.rs` checks kernel
sources in this order on the eager path (inline, per-session):

| Priority | Source | Platform | Mechanism |
|---|---|---|---|
| 1 | eBPF | Linux | O(1) lookup in the kernel-space `l7_connections` hash map |
| 2 | ETW | Windows | O(1) lookup in the userspace connection table, then lineage enrichment |
| 3 | ES+libproc | macOS | Iterate ES-known PIDs, probe sockets via libproc |

The three are tried in that fixed order in `try_kernel_resolve`. Only one can
be compiled in on a given platform, so the ordering is not a precedence
decision between competing sources.

If no kernel source resolves the session, it is queued for batch resolution
using `netstat2` socket scanning + sysinfo enrichment. On Windows without
the `etw` feature, sessions go directly to the batch path where
`GetExtendedTcpTable` resolves them reliably.

The `L7ResolutionSource` enum tracks which source resolved each session:

```rust
pub enum L7ResolutionSource {
    Unknown,                // Before any attempt, or a failure short of max retries
    ExactMatch,             // netstat2 socket scan matched the full tuple
    CacheHitRunning,
    CacheHitTerminated,     // Within the PID-reuse grace period
    HostCacheHitRunning,
    HostCacheHitTerminated,
    FailedMaxRetries,
    Ebpf,                   // eBPF connection map (Linux)
    EndpointSecurity,       // ES process table + targeted libproc (macOS)
    Etw,                    // ETW connection table (Windows)
    MacosLibproc,           // PROC_PIDFDSOCKETINFO (macOS)
}
```

## Benchmark Results

Benchmarks run in CI on all three platforms (`tests/l7_benchmark_test.rs`),
each with and without its kernel-level L7 feature.  Every session is a real
TCP connection opened from the test process itself (`TcpStream::connect` to
`1.1.1.1:80`), held open for a controlled duration, then closed.  The local
port is known immediately from `local_addr()` -- no `lsof`/`netstat`
dependency for port discovery.

CI workflow: `.github/workflows/l7_benchmark.yml` (macos-14, ubuntu-latest,
windows-latest).  GitHub `macos-14` runners have **SIP disabled**.

### Resolution Rate by Session Duration

Percentage of sessions attributed to the correct process, across a realistic
mix of connection lifetimes (3 iterations per bucket).

| Hold duration | Linux eBPF | Linux none | macOS ES | macOS none | Windows ETW | Windows none |
|---|---|---|---|---|---|---|
| 0 ms (instant close) | **100%** | 0% | 0% | 0% | **100%** | **100%** |
| 10 ms (fast API) | **100%** | 0% | 0% | 0% | **100%** | **100%** |
| 50 ms (HTTPS handshake) | **100%** | **100%** | **100%** | 33% | **100%** | **100%** |
| 200 ms (moderate API) | **100%** | **100%** | **100%** | **100%** | **100%** | **100%** |
| 500 ms (download) | **100%** | **100%** | **100%** | **100%** | **100%** | **100%** |
| 1 s (page load) | **100%** | **100%** | **100%** | **100%** | **100%** | **100%** |
| 3 s (long call) | **100%** | **100%** | **100%** | **100%** | **100%** | **100%** |
| **Overall** | **100%** | **71%** | **71%** | **62%** | **100%** | **100%** |

**Key findings**:

- Without kernel L7, sessions shorter than ~50 ms are invisible to the
  resolver on Linux and macOS.
- With eBPF on Linux, the process is already in the kernel event table
  before the connection even completes: **100% resolution at 0 ms**.
- On macOS, ES provides a measurable reliability improvement at the 50 ms
  boundary: **100% vs 33%** at 50 ms hold, and **71% vs 62%** overall.
  The ES eager path (`get_l7_for_session`) iterates only kernel-known PIDs
  via libproc, which is faster and more reliable than the full system scan.
- Windows `netstat2` is fast enough to resolve even instant-close connections
  on both paths.

### Minimum Detectable Session Duration

Binary search: shortest TCP connection (held for N ms then closed) that the
resolver can still attribute (majority of 3 attempts must succeed).

| Platform | With kernel L7 | Without kernel L7 | Improvement |
|---|---|---|---|
| **Linux** | **0 ms** (eBPF) | 50 ms (netstat2) | Infinite -- detects sessions the polling path cannot see |
| **macOS** | 50 ms (ES + libproc) | 50 ms (libproc) | Same floor but higher reliability at boundary (100% vs 33% at 50 ms) |
| **Windows** | 0 ms (ETW + netstat2) | 0 ms (netstat2) | Same floor -- netstat2 is already fast enough on Windows |

### Resolution Source and Latency

How quickly the resolver returns a result once the session is known.

| Platform | With kernel L7 | Without kernel L7 |
|---|---|---|
| **Linux** | **Ebpf, <1 ms** (from pre-populated DashMap, eager path) | ExactMatch, <1 ms for active / timeout for <50 ms |
| **macOS** | **EndpointSecurity, <1 ms** (ES-targeted libproc, eager path) | MacosLibproc, <1 ms for active / timeout for <50 ms |
| **Windows** | ExactMatch, ~107 ms (0 ms hold) to 0 ms (>20 ms hold) | ExactMatch, ~115 ms (0 ms hold) to 0 ms (>20 ms hold) |

All three kernel-level sources now participate in the eager resolution path
(`add_connection_to_resolver_ex` and `get_resolved_l7` in `l7.rs`), meaning
they are tried inline before the session is queued for batch resolution.

## Feature Flags

| Feature | Platform | What it enables | Enabled by default |
|---|---|---|---|
| `ebpf` | Linux (x86_64, aarch64) | eBPF process attribution | Yes (posture, helper) |
| `endpointsecurity` | macOS | Endpoint Security process table | Yes (posture, helper) |
| `etw` | Windows | ETW kernel trace: process lineage, file-writer attribution, task access | Yes (posture, helper) |
| `packetcapture` | All | Packet capture (required for any L7) | Yes |
| `asyncpacketcapture` | All | Async capture mode | Yes |

`ebpf` and `endpointsecurity` are enabled in production because they provide
measurable improvements over the polling fallback. `etw` is enabled for the
kernel-time evidence it carries, not for L7 resolution, which `netstat2`
already handles on Windows. See the ETW section below.

## Deployment

### edamame_helper (privileged daemon)

`edamame_helper` runs with the necessary privileges on each platform and
enables kernel-level L7 features where they add value:

```toml
flodbadd = { features = ["packetcapture", "asyncpacketcapture", "endpointsecurity", "fim", "etw"] }
```

On macOS, the helper binary must be codesigned with the Endpoint Security
entitlement (`macos/edamame_helper.entitlements`), and AMFI additionally
requires a provisioning profile at runtime. On Windows, the helper runs as a
Windows Service under LocalSystem, which is what the ETW kernel trace session
needs. On Linux, it runs as root.

### edamame_posture (standalone CLI)

`edamame_posture` enables kernel-level features per platform:

- **Linux**: `ebpf` (x86_64/aarch64 only)
- **macOS**: `endpointsecurity`, `fim`
- **Windows**: `etw`
- **Other**: baseline `packetcapture` only

The `fim` feature reaches every platform regardless, because Cargo features
are additive and `edamame_core` forwards it through `edamame_foundation`. The
per-target lines above add to that, they do not restrict it.

### Singleton Pattern

Each kernel-level module uses `OnceCell<FlodbaddL7{Ebpf,Es,Etw}>` for
singleton initialization. The `init()` call spawns a background thread
that:
1. Initializes the kernel client (eBPF programs, ES client, ETW session)
2. Subscribes to events
3. Populates the process/connection tables
4. Sets `AtomicBool` availability flag

The `is_available()` function checks this flag to determine if the kernel
source can be used for resolution.

## Known Limitations

1. **Short-lived sessions on macOS**: Connections shorter than ~50 ms are
   invisible to the ES+libproc eager resolution path.  ES provides the PID
   set, but libproc socket probing is the bottleneck.  ES does not expose
   TCP/IP connection events.  Apple's Network Extension framework could
   provide per-flow PID mapping but requires additional entitlements.

2. **Short-lived sessions on Linux without eBPF**: Same 50 ms floor as macOS.
   `netstat2` polling cannot observe sockets that have already closed.
   With eBPF, this is fully solved (0 ms detection).

3. **ES entitlement**: macOS Endpoint Security requires a provisioned entitlement
   from Apple. Without it, the ES client fails to initialize and the system falls
   back to `libproc`. Ad-hoc signing works only with SIP disabled (confirmed on
   GitHub `macos-14` runners).

4. **UDP attribution**: Linux eBPF and macOS libproc provide UDP socket-to-PID.
   On Windows, `netstat2` (`GetExtendedUdpTable`) handles UDP attribution.

## Re-arming exhausted resolutions

A session whose resolution attempts are exhausted is marked `FailedMaxRetries`
and would otherwise stay unattributed for its whole lifetime. That is the wrong
answer for a long-lived flow whose process simply was not visible during the
initial retry window; attribution latency of 40 to 130 seconds is routine on
the CI gate hosts.

`populate_l7` therefore re-arms exhausted resolutions, but only for sessions
worth a resolver round. Each re-arm costs a shared process-table and
socket-table refresh, and CI hosts carry hundreds of local and system flows
that never attribute.

| Condition | Value |
|---|---|
| Session still active | required |
| Destination non-local | required |
| Bytes carried, either direction | >= 1024 (`L7_REQUEUE_MIN_SESSION_BYTES`) |
| Cadence | 15 s (`L7_REQUEUE_INTERVAL_SECS`) |
| Rounds | 8, about 2 minutes (`MAX_L7_REQUEUE_ROUNDS`) |

An earlier version re-armed every unattributed session on every pass at a 5 s
cadence. That moved the posture perf gate: ubuntu-x64 capture and lanscan rose
20 to 45 percent, `all` rose 25 percent, and ubuntu-arm64 capture rose 35 to 45
percent on the three builds carrying it. The current shape covers the same
attribution latency without the churn. Both constants read an environment
override for experiments.

## ETW and Windows L7

ETW does not improve Windows L7 socket attribution, and the benchmarks in this
document are the evidence:

- `GetExtendedTcpTable` is a synchronous kernel syscall returning every active
  TCP connection with its owning PID in one call. It sees a connection
  immediately after it is established.
- ETW kernel trace events are delivered asynchronously with buffering latency.
  The TCP/IP Connect event reaches the callback thread after the connection is
  already visible to `GetExtendedTcpTable`.
- Windows resolves 100 percent of sessions at a 0 ms hold both with and without
  ETW, and the primary resolution source is always `ExactMatch`, never `Etw`.
  ETW is tried first on both paths, so this is a measured outcome rather than
  an ordering decision. See the IPv4 decode caveat in `ETW.md`.

What changed since that conclusion was first written is the rest of the
picture. ETW is now enabled in production for three things it is genuinely the
only source of on Windows:

| Capability | Why ETW |
|---|---|
| Kernel-time file-writer attribution | The FileIo session names the writer at write time, which no polling API can do once the writer has closed the file |
| Cross-process task access | `PsOpenProcess` from `Microsoft-Windows-Kernel-Audit-API-Calls` is the Windows equivalent of macOS task ports and the Linux `ptrace_may_access` kprobe |
| Process metadata for exited processes | Image path and command line captured at process start, which `sysinfo` cannot recover afterwards |

The operational costs named in the original conclusion are real and unchanged:
the NT Kernel Logger session is exclusive and conflicts with PerfMon, Xperf and
ProcMon, and Administrator or LocalSystem is required. See `ETW.md`.
