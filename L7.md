# L7 Process Attribution

Flodbadd provides per-session Layer 7 (L7) process attribution: mapping every
observed TCP/UDP session to the originating process, its path, parent process,
command line, and open files. This is the foundation for EDAMAME's vulnerability
detection and behavioral divergence analysis.

## Architecture

L7 resolution follows a priority chain, falling back to the next source when
the previous one has no data for a given session:

```
Kernel-level (eBPF / ES / ETW)
        |
        v
Platform socket lookup (libproc on macOS, netstat2 on Windows/Linux)
        |
        v
sysinfo enrichment (process metadata)
```

The kernel-level sources maintain persistent process and connection tables
that survive short-lived connections; the platform socket lookups are
point-in-time snapshots that can miss processes that have already exited.

## Platform Support

### Linux -- eBPF

| Aspect | Detail |
|---|---|
| Module | `src/l7_ebpf.rs` |
| Feature flag | `ebpf` |
| Documentation | `EBPF.md` |
| Mechanism | eBPF programs attached to `tracepoint/sched/sched_process_exec` and `tracepoint/sched/sched_process_exit` |
| Data maintained | `DashMap<u32, EbpfProcessInfo>` (PID -> process name, path, parent) |
| Connection mapping | Not provided -- eBPF tracks processes only; socket-to-PID still uses `/proc/net/tcp` or `netstat2` |
| Privilege | `CAP_BPF` + `CAP_PERFMON` (or root) |
| Architectures | x86_64, aarch64 |
| Limitations | Requires kernel >= 5.8, clang/llvm at build time, linux-headers for BTF |

### macOS -- Endpoint Security (ES)

| Aspect | Detail |
|---|---|
| Module | `src/l7_es.rs` |
| Feature flag | `endpointsecurity` |
| Documentation | `ENDPOINTSECURITY.md` |
| Mechanism | ES client subscribing to `NOTIFY_FORK`, `NOTIFY_EXEC`, `NOTIFY_EXIT` events |
| Data maintained | `DashMap<u32, EsProcessInfo>` (PID -> process name, path, parent PID, parent name, parent path) |
| Connection mapping | Not provided -- ES tracks processes only; socket-to-PID uses `libproc` (`src/l7_macos.rs`) |
| Privilege | Requires `com.apple.developer.endpoint-security.client` entitlement + root |
| Entitlement | Must be provisioned by Apple; ad-hoc signing works with SIP disabled |
| Fallback | Without ES, `l7_macos.rs` provides socket-to-PID via `libproc` plus `sysinfo` for metadata |

The hybrid ES + `libproc` approach:
1. `libproc` resolves socket -> PID (fast, reliable for active connections)
2. ES process table enriches PID -> full metadata (name, path, parent chain)
3. If ES is unavailable, `sysinfo` provides weaker metadata for the PID

### Windows -- Event Tracing for Windows (ETW)

| Aspect | Detail |
|---|---|
| Module | `src/l7_etw.rs` |
| Feature flag | `etw` |
| Documentation | `ETW.md` |
| Mechanism | Kernel ETW trace session ("NT Kernel Logger") subscribing to `Microsoft-Windows-Kernel-Process` and TCP/IP providers |
| Data maintained | `DashMap<u32, EtwProcessInfo>` (PID -> image path, parent PID, command line) and `DashMap<TcpConnectionKey, u32>` (connection -> PID) |
| Connection mapping | Provided by TCP/IP ETW events (Connect, Accept, Reconnect) |
| Privilege | Administrator required for kernel trace session |
| Fallback | Without ETW, `netstat2` provides socket-to-PID polling + `sysinfo` for metadata |

ETW is unique in providing both process lifecycle AND connection-to-PID mapping
from a single event stream, eliminating the race condition between connection
setup and PID discovery that affects the polling approach.

## Resolution Source Priority

The `FlodbaddL7::get_resolved_l7()` method in `src/l7.rs` checks sources in
this order for each session:

| Platform | Priority 1 | Priority 2 | Priority 3 |
|---|---|---|---|
| **Linux** | eBPF process table + netstat2 socket lookup | netstat2 + sysinfo | -- |
| **macOS** | ES process table + libproc socket lookup | libproc + sysinfo | -- |
| **Windows** | ETW connection table + process table | netstat2 + sysinfo | -- |

The `L7ResolutionSource` enum tracks which source resolved each session:

```rust
pub enum L7ResolutionSource {
    Ebpf,              // eBPF process table (Linux)
    EndpointSecurity,  // ES process table (macOS)
    Etw,               // ETW connection+process table (Windows)
    MacosLibproc,      // libproc socket-to-PID (macOS)
    Netstat,           // netstat2 polling (cross-platform)
    Sysinfo,           // sysinfo metadata enrichment
    Cache,             // Previously resolved, served from cache
}
```

## Benchmark Results

Cross-platform benchmarks run in CI (`tests/l7_benchmark_test.rs`). The test
suite includes curl-based scenarios (requiring external port discovery via
`lsof`/`netstat`) and a `self_connect_tcp` scenario that opens a TCP connection
from the test process itself (no external port discovery needed -- most reliable).

CI workflow: `.github/workflows/l7_benchmark.yml` (macOS-14, ubuntu-latest,
windows-latest). GitHub Actions `macos-14` runners have **SIP disabled**.

### macOS CI -- Endpoint Security (macos-14, aarch64)

The benchmark binary is ad-hoc codesigned with the ES entitlement in CI.
Since SIP is disabled on `macos-14` runners, ad-hoc signing grants ES access.

| Scenario | With ES | Without ES |
|---|---|---|
| | Source / Resolved / Latency | Source / Resolved / Latency |
| medium_lived_curl | EndpointSecurity 3/3 74ms | MacosLibproc 3/3 51ms |
| long_lived_curl | EndpointSecurity 2/2 54ms | MacosLibproc 2/2 54ms |
| **self_connect_tcp** | **EndpointSecurity 5/5 53ms** | **MacosLibproc 5/5 54ms** |

**Analysis**: ES is active and resolving sessions through the kernel process table.
Resolution latency is comparable to `libproc` (~50-70ms). The `self_connect_tcp`
scenario achieves 100% resolution with correct process name attribution on both
paths. Curl-based short-lived and burst scenarios fail due to `lsof` port discovery
timing (the connection closes before lsof can observe it), not an L7 resolver issue.

### Linux CI -- eBPF (ubuntu-latest, x86_64)

| Scenario | With eBPF | Without eBPF |
|---|---|---|
| | Source / Resolved / Latency | Source / Resolved / Latency |
| **self_connect_tcp** | **Ebpf 5/5 <1ms** | **ExactMatch 5/5 61ms** |

**Analysis**: eBPF provides **sub-millisecond** resolution from its kernel event
cache -- the process info is already in the `DashMap` when the resolver queries it.
Without eBPF, the fallback `ExactMatch` (netstat2 socket lookup) resolves at ~61ms.
The curl-based scenarios all show `no_port_discovered` because the `lsof`/`/proc/net/tcp`
port discovery races against connection teardown; this is a test infrastructure
limitation. The `self_connect_tcp` scenario bypasses this entirely by knowing
its own local port. eBPF kernel_l7_available=true confirms the eBPF programs
load and run correctly on GitHub `ubuntu-latest` runners.

### Windows CI -- ETW (windows-latest, x86_64)

| Scenario | With ETW | Without ETW |
|---|---|---|
| | Source / Resolved / Latency | Source / Resolved / Latency |
| short_lived_curl | ExactMatch 2/3 109ms | ExactMatch 3/3 109ms |
| medium_lived_curl | ExactMatch 3/3 108ms | ExactMatch 3/3 107ms |
| long_lived_curl | ExactMatch 2/2 107ms | ExactMatch 2/2 119ms |
| short_lived_curl_https | ExactMatch 3/3 108ms | ExactMatch 3/3 111ms |
| burst_curl | ExactMatch 5/5 104ms | ExactMatch 5/5 104ms |
| **self_connect_tcp** | **ExactMatch 5/5 108ms** | **ExactMatch 5/5 127ms** |

**Analysis**: ETW successfully initializes (`kernel_l7: "etw"`,
`kernel_l7_available: true`). Both paths currently resolve via `ExactMatch`
(netstat) since the netstat polling cycle finds the connection before the ETW
event is processed. The ETW path shows a slight latency improvement (108ms vs
127ms for self_connect_tcp). Windows port discovery via `netstat -ano` is
significantly more reliable than Unix `lsof`, resolving even short-lived curl
connections. Future work: the ETW `DashMap<TcpConnectionKey, u32>` maintains
persistent connection-to-PID mappings that will improve attribution of
connections that close before netstat polling.

### Cross-Platform Summary

| Platform | Kernel L7 | Available | Best Latency | Fallback Latency |
|---|---|---|---|---|
| Linux (eBPF) | ebpf | yes | **<1ms** (from event cache) | 61ms (ExactMatch) |
| macOS (ES) | endpointsecurity | yes | **53ms** (ES + libproc) | 54ms (MacosLibproc) |
| Windows (ETW) | etw | yes | **108ms** (ExactMatch + ETW) | 127ms (ExactMatch) |

All three kernel-level L7 mechanisms initialize and run correctly in CI.
eBPF provides the strongest improvement (sub-millisecond from pre-populated
kernel tables). ES and ETW augment the existing socket lookup with richer
process metadata and persistent connection tables.

## Feature Flags

| Feature | Platform | What it enables |
|---|---|---|
| `ebpf` | Linux (x86_64, aarch64) | eBPF process attribution |
| `endpointsecurity` | macOS | Endpoint Security process table |
| `etw` | Windows | ETW kernel trace (process + TCP connection mapping) |
| `packetcapture` | All | Packet capture (required for any L7) |
| `asyncpacketcapture` | All | Async capture mode |

All kernel-level features are additive. When unavailable at runtime (missing
privileges, missing entitlement, etc.), the system gracefully falls back to
platform socket lookup + sysinfo.

## Deployment

### edamame_helper (privileged daemon)

`edamame_helper` runs with the necessary privileges on each platform and
enables all kernel-level L7 features:

```toml
flodbadd = { features = ["packetcapture", "asyncpacketcapture", "endpointsecurity", "etw"] }
```

On macOS, the helper binary must be codesigned with the Endpoint Security
entitlement (`macos/edamame_helper.entitlements`). On Windows, the helper
runs as a Windows Service (Administrator). On Linux, it runs as root.

### edamame_posture (standalone CLI)

`edamame_posture` enables kernel-level features per platform:

- **Linux**: `ebpf` (x86_64/aarch64 only)
- **macOS**: `endpointsecurity`
- **Windows**: `etw`
- **Other**: baseline `packetcapture` only

### Singleton Pattern

Each kernel-level module uses `OnceCell<FlodbaddL7{Ebpf,Es,Etw}>` for
singleton initialization. The `init()` call spawns a background thread
that:
1. Initializes the kernel client (eBPF programs, ES client, ETW session)
2. Subscribes to events
3. Populates the process/connection tables
4. Sets `AtomicBool` availability flag

The `is_available()` function checks this flag to determine if the kernel
source can be used for resolution.

## Known Limitations

1. **Short-lived processes**: Connections from processes that exit before the
   polling resolver can discover the ephemeral port are missed by `netstat2`/`lsof`.
   Kernel-level sources (eBPF, ES, ETW) maintain tables that survive process exit,
   improving attribution for these cases.

2. **ES entitlement**: macOS Endpoint Security requires a provisioned entitlement
   from Apple. Without it, the ES client fails to initialize and the system falls
   back to `libproc`. Ad-hoc signing works only with SIP disabled (confirmed on
   GitHub `macos-14` runners).

3. **ETW kernel session**: Only one "NT Kernel Logger" session can exist at a time.
   If another application (e.g., performance monitor) holds the session, ETW
   initialization will attempt to stop the existing session. If that fails, it
   falls back to `netstat2`.

4. **UDP attribution**: Linux eBPF and macOS libproc provide UDP socket-to-PID.
   Windows ETW provides TCP only; UDP sessions fall back to `netstat2`.

5. **Benchmark port discovery**: The curl-based benchmark scenarios use `lsof`
   (macOS), `/proc/net/tcp` (Linux), or `netstat -ano` (Windows) to discover
   ephemeral ports. Fast connections that close before discovery will show
   `no_port_discovered`. The `self_connect_tcp` scenario avoids this entirely
   by opening a TCP connection from the test process and reading its own
   `local_addr()` directly.
